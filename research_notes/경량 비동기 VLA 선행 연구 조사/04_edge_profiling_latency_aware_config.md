# Edge-hardware profiling of VLA models and latency-aware choice of inference settings (state of the literature as of 2026-11-16)

Source-status legend used on every bullet:
- **[P]** = read in this session from the primary page (arXiv abs/HTML, official docs, model card, repo docs). Numbers were extracted by an automated page reader, so spot-check table values against the PDF before quoting them in a paper.
- **[S]** = secondary only (search-result snippet, aggregator, or third-party summary); not verified against the primary text.
- **[B]** = well-known background paper, not re-fetched in this session.

Candidate idea under test: *"Freshness-versus-fidelity configuration per device: choose the number of flow/denoising steps, input resolution, replan interval and chunk length to maximize closed-loop task success under the device's measured latency, rather than open-loop accuracy — because a more accurate but slower setting acts on older observations."*

---

## 1. What exactly do the named papers report (per-paper dense notes; SmolVLA numbers on Jetson Orin Nano / NX / AGX)?

### Takeaway
Component-level edge profiling of VLAs is now a crowded area (VLA-HWBench, VLA-Perf, XPUs, vla.cpp, EagleVLA/Jetson-PI, a NeurIPS-2026 workshop paper on a 450M VLA), and SmolVLA has public latency numbers on Orin Nano 8GB, AGX Orin and AGX Thor. None of the named profiling papers selects inference settings per device against closed-loop success; almost all report latency/Hz only, and the SmolVLA paper itself reports no latency at all.

### Cited Findings

**VLA-HWBench — "Where the Time Goes When VLA Models Run on Edge Hardware" (arXiv 2610.34717; v1 26 Oct 2026, v2 27 Oct 2026; Xu, Tan, Jiang, He, Wu, Zeng, Heinrich)**
- [P] Measures 18 open VLAs (19 configurations) on exactly two platforms: NVIDIA Jetson AGX Thor (T5000) and AMD Ryzen AI Max+ PRO 395. No Orin Nano / Orin NX / AGX Orin measurements (AGX Orin appears only in related work). — [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2)
- [P] Seven-stage breakdown: S0 CPU preprocessing, S1 host-to-device copy, S2 vision encoding, S3 prefill (LM, KV cache), S4 action generation (denoise steps or decoded tokens), S5 CPU postprocessing, S6 residual (incl. Python dispatch between stages). — [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2)
- [P] SmolVLA is included (0.45B, flow matching, chunk 50, 3 camera views, LeRobot 0.6.1, PyTorch eager reference; Jetson: CUDA 13.2 / PyTorch 2.11). Thor p50 = 191 ms (p5–p95 187–195); AMD p50 = 140 ms. Thor stage split (ms): S0 4.3 / S2 vision 20.9 / S3 prefill 15.0 / **S4 action generation 146.6** / S5 0.1 / S6 0.2 (total 187). AMD: S0 0.7 / S2 40.8 / S3 10.9 / S4 87.5. — [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2)
- [P] SmolVLA denoise-step sweep, linear fit latency = a + b·steps: Thor eager b = 14.5 ms/step, a = 41 ms (R² = 1.000); AMD b = 8.6 ms/step, a = 54 ms. With torch.compile the per-step cost on Thor drops to 2.7 ms (reduce-overhead) / 2.4 ms (max-autotune); AMD 5.9 ms. End-to-end SmolVLA on Thor: 191 → 66.4 ms (2.88×, reduce-overhead) or 71.9 ms (2.66×, max-autotune); AMD 140 → 109 ms (1.28×) / 77.7 ms (1.80×). — [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2)
- [P] Headline findings: (1) action-generation strategy matters more than model size — parameter count explains at most 15% of latency variance; long chunks in few flow steps keep up with control, token-by-token decoding often does not; (2) kernel fusion + 4-bit weights give the largest speedups (≈2.6–2.9× over torch.compile) but only for π0.5 and GR00T N1.7 and only on Jetson; optimization shifts time to CPU preprocessing (39% of the GR00T N1.7 call); (3) after optimization, memory bandwidth limits only the few-token denoising-type stages, software overhead limits the other stages. Recommendation: "few action-generation iterations", wider kernel fusion/low-bit, fast host CPU and high memory bandwidth. — [arXiv 2610.34717 abs](https://arxiv.org/abs/2610.34717)
- [P] Other stacks: π0.5 Thor 405 → 157 ms with torch.compile (2.58×); FlashRT (fused kernels inside CUDA graphs) 405 → 72.8 ms (5.56× over eager); π0.5 best total 318 → 44 ms (7.2×); GR00T N1.7 119 → 96.2 ms with TensorRT (1.24×), 119 → 46 ms best (2.6×). The π0.5 compile path captured the whole call in one CUDA graph, cutting kernel launches from ~13k to 15. ONNX Runtime not covered. — [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2)
- [P] Limitations: **no closed-loop task success is measured** (latency + action-agreement only; compiled SmolVLA cosine-sim min 0.9695 / median 0.9993 on Thor; one compiled π0.5 run flipped a gripper command); latency measured on one LIBERO-10 observation plus 24 frames of one episode; fused/4-bit backends cover only two models on Jetson. The paper does not interpret the fixed intercept or per-step cost of SmolVLA as dispatch overhead. — [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2)

**VLA-Perf — "How Fast Can I Run My VLA?" (arXiv 2602.18397; 20 Feb 2026; Jiang, Clemons, Sankaralingam, Kozyrakis)**
- [P] An **analytical roofline model**, not a measurement study: per-operator latency = max(FLOPs/peak FLOP/s, bytes/peak bandwidth). Validated only against a Triton π0 implementation on RTX 4090 (10 flow steps, chunk 63): roofline 14.7/22.5/30.4 ms vs real 20.0/27.3/36.8 ms for 1/2/3 cameras (73–83% fidelity). — [arXiv 2602.18397 HTML](https://arxiv.org/html/2602.18397)
- [P] Models: π0 (SigLIP-So 0.4B + Gemma-2B + 0.3B expert) and hypothetical scaled variants; **SmolVLA only in related work**. Hardware: Jetson Thor, RTX 4090, A100, H100, B100 — **no Orin variants**. Predicted π0 on Thor: vision 6.06 / VLM 20.30 / action 26.20 ms = 52.57 ms (19.0 Hz); RTX 4090 31.06 ms (32.2 Hz). — [arXiv 2602.18397 HTML](https://arxiv.org/html/2602.18397)
- [P] Action expert is memory-bound on every platform (54 FLOPs/byte vs 321 vision, 543 VLM); on Thor all three components are memory-bound. Denoising steps scale action latency linearly (10 → 50 steps: 5× action latency, 2.15× end-to-end); chunk size 50 → 250 raises action latency only ~40% and end-to-end ~11% (takeaway 6: steps matter, chunk size negligible). — [arXiv 2602.18397 HTML](https://arxiv.org/html/2602.18397)
- [P] Limitations: assumes ideal software; **kernel-launch latency, OS interference and runtime-library overhead are explicitly not modeled**; no task success is measured; the effect of async staleness on control stability/success is explicitly left to future work; execution horizon is defined but its effect is not quantified. — [arXiv 2602.18397 HTML](https://arxiv.org/html/2602.18397)

**"Characterizing Vision-Language-Action Models across XPUs" (arXiv 2604.24447; 27 Apr 2026; Zhou, Chen, Peng, Li, Li, Gu; 13 pp)**
- [P] Hardware: RTX 4090, Jetson Thor, Jetson AGX Orin (64 GB), Intel B60 Pro, Ascend 310B/310P NPUs; **no Orin Nano / NX**. Models with numbers: π0, π0.5, OpenVLA, Diffusion Policy; SmolVLA/GR00T/ACT appear only in figures (no numeric SmolVLA result in the text). — [arXiv 2604.24447 HTML](https://arxiv.org/html/2604.24447)
- [P] π0 latency (PyTorch): RTX 4090 102.3 ms, Thor 246.0 ms, **AGX Orin 920.6 ms**, B60 Pro 306.5 ms, Ascend 310P 818.0 ms. torch.compile: 4090 102.3 → 35.2 ms (2.90×); Thor 246 → 163 ms (1.51×); Ascend ATC 818 → 350 ms (2.34×). — [arXiv 2604.24447 HTML](https://arxiv.org/html/2604.24447)
- [P] Two-phase pattern: compute-bound VLM backbone (>90% SM utilization, ≈840 FLOPs/byte) followed by memory-bound action expert (20–40% SM utilization, 64.5 FLOPs/byte); action expert takes ≈2× the backbone's latency for π0. No per-denoise-step latencies; TensorRT/ONNX not used. — [arXiv 2604.24447 HTML](https://arxiv.org/html/2604.24447)
- [P] Proposes DP-Cache (reuse diffusion-step results) and V-AEFusion (run early denoise steps on the previous observation's stale KV cache). Stale-step sweep on a real JAKA arm (50 trials/task, block/cup): 0 stale steps 92/86%, 5 → 88/78%, 6 → 80/66%, 7 → 50/42%. V-AEFusion speedup is device-dependent (4090 1.32×, Orin 920 → 806 ms = 1.14×, Thor 1.04×). — [arXiv 2604.24447 HTML](https://arxiv.org/html/2604.24447)
- [P] Limitation: Hz and success come from separate experiments; no per-run latency–success relationship; stable-window fixed offline, not adaptive. — [arXiv 2604.24447 HTML](https://arxiv.org/html/2604.24447)

**vla.cpp — "A Unified Inference Runtime for Vision-Language-Action Models" (arXiv 2606.08094; v1 6 Jun 2026, v2 21 Sep 2026; Nguyen et al., VinRobotics; 8 pp)**
- [P] C++ runtime (llama.cpp/GGUF lineage, no PyTorch at execution) for 11 VLAs: SmolVLA, Evo-1, π0, π0.5, GR00T N1.5/1.6/1.7, VLA-JEPA, VLA-Adapter, OpenVLA-OFT, BitVLA. Devices include **Jetson Orin Nano 8 GB**, Jetson AGX Orin, RTX 3060/3090/4070/5070, Apple M4, Intel Arc, CPUs. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] SmolVLA closed-loop on LIBERO-Object (200 episodes, execution horizon S=4), ms per executed action and successes: RTX 3060 28.16 ms (181/200); AGX Orin 65.41 ms (181/200); **Orin Nano 141.81 ms (176/200)**, peak RSS 2031 MiB on the Nano. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] SmolVLA runtime comparison (desktop only): RTX 3090 server latency vla.cpp 55.8 ms vs PyTorch eager 174.1 ms vs torch.compile 65.9 ms; RTX 5070 74.11 ms (vla.cpp) vs 175.99 ms (eager) vs 76.26 ms (graph-captured PyTorch). RTX 5070 time split at T=10: vision 38%, backbone 14%, expert ≈ remainder (~48%). No absolute vision/prefix/expert split for SmolVLA on Jetson in the paper. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] **Execution-horizon sweep, SmolVLA, LIBERO-Object, Orin Nano, chunk H=50, 50 episodes per setting** (S, median call latency, Hz=S/L, success): S=1 358 ms 2.8 Hz 82%; S=2 353 ms 5.7 Hz 86%; S=4 357 ms 11.2 Hz 94%; S=8 392 ms 20.4 Hz 88%; S=16 447 ms 35.8 Hz **98%**; S=32 457 ms 70.1 Hz 80%; S=50 457 ms 109.4 Hz 38%. Non-monotonic; unadjusted Fisher test p = 0.0078 for S=16 vs S=32. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] Denoise-step sweep (GR00T N1.7, RTX 3060, 100 episodes): T=1/2/4/8/16 → success 99/95/98/98/95 (runtime) and 96/98/94/95/97 (PyTorch); backbone+head time ≈ 13.9 + 5.8·T ms. At T=1 the max action difference vs T=4 was 0.93 despite 99/100 successes. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] Delay injection (GR00T N1.7, ALOHA, RTX 4070, 10 episodes/condition): 0–2000 ms injected delay, success 9/10–10/10 throughout (authors note low sensitivity at n=10). UR10e + SmolVLA (S=25, 20 Hz, 20 episodes/backend): round-trip latency 111 ms → 3653 ms across backends, executed rate 17.7 → 5.0 Hz, blocked-on-prediction time 8% → 73%, success CUDA 15/20, Metal 12/20, i9 12/20, Ryzen 14/20. Rate model f_exec ≈ S/(L_rt + S·Δt). — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] SmolVLA precision case study: computing vision position-embedding indices at a different precision shifted indices; matching the half-precision reference cut position-embedding relative error 0.32 → 0.003 and raised LIBERO-Object task-0 success from 2/10 to 9/10. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] Stated limitations: the paper does **not** test whether the best execution horizon depends on latency or device (it says only that runtime comparisons should specify both S and T); small quasi-static robot studies; largest models exceed the Nano's memory. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] Repo benchmark report for **Jetson Orin Nano Super (CUDA, MAXN_SUPER, JetPack 6.2.2, dated 2026-09-30)**: SmolVLA, 2 views × 512 px, 10 flow steps, chunk 50: min/p50/p90 = 462.8/463.9/466.1 ms at defaults, **vision 298.6 ms**, peak RSS 2488 MiB; fastest flags (`--flash-attn --mm-prec default`) 286.7 ms with vision 173.1 ms, RSS 1676 MiB (the doc warns these flags can change the action chunk). Same table: π0 845 ms, π0.5 850 ms, GR00T N1.7 272 ms, VLA-Adapter 298 ms, BitVLA 335 ms, Octo-Small 32 ms on the Nano. Only vision time is broken out; no prefix/expert/per-step split. — [vla.cpp docs/benchmark/jetson-orin-nano.md](https://raw.githubusercontent.com/VinRobotics/vla.cpp/main/docs/benchmark/jetson-orin-nano.md)
- [P] Repo benchmark index: SmolVLA min latency 164.3 ms on Jetson AGX Orin (CUDA) and 462.8 ms on Orin Nano Super. — [vla.cpp docs/benchmark](https://github.com/VinRobotics/vla.cpp/tree/main/docs/benchmark)

**RhinoVLA Technical Report (arXiv 2606.07383; v1 5 Jun 2026, v4 17 Jul 2026; Huixi Technology)**
- [P] Co-design with the Huixi R1 edge SoC (7 nm, 500 TOPS INT8, "200 GB/s-class" bandwidth). RhinoVLA on R1: vision (3 views) 24.31 ms (28.4%), VLM backbone 20.78 ms (24.3%), action expert 36.71 ms (42.9%), other 3.74 ms; total 85.54 ms = 11.69 Hz (baseline 5.84 Hz). Parallel vision encoding 34.52 → 24.31 ms. Number of denoise steps and per-step latency not reported. — [arXiv 2606.07383 HTML](https://arxiv.org/html/2606.07383v4)
- [P] Reference profile of π0.5 on Jetson AGX Orin (PyTorch SDPA): ≈858.3 ms total = vision 69.3 / VLM 528.0 / action expert 257.0 ms. Token argument: Qwen3-VL gives 64 merged visual tokens per image vs 256 for PaliGemma-224. No SmolVLA latency (only its LIBERO 88.8% average). Latency and success are reported separately; no success-vs-control-frequency test. The fetched text contains internal numeric inconsistencies (e.g., LIBERO 94.1% in text vs 96.6% in table). — [arXiv 2606.07383 HTML](https://arxiv.org/html/2606.07383v4)

**"Rethinking Small VLM Quantization: From Component-Wise Analysis to Hardware-Aware Edge Deployment" (arXiv 2607.08029; 9 Jul 2026; ICML 2026 Workshop on Hypothesis Testing)**
- [P] VLM-only (no VLA, no robot control): Qwen3-VL-2B, DeepSeek-VL2-Tiny, PaliGemma2-3B, LLaVA-OV-0.5B, Kosmos-2.5 on **Jetson Orin NX 16 GB (25 W)** and **AGX Orin 64 GB (50 W)**; **Orin Nano excluded due to OOM**. Stack: BitsAndBytes INT8/INT4, NVTX + Nsight Systems, JetPack 6.2.1; no TensorRT/ONNX/llama.cpp. — [arXiv 2607.08029 HTML](https://arxiv.org/html/2607.08029)
- [P] SigLIP vision-encoder INT8 anomaly: PaliGemma2 (SigLIP-So400m) FP16 → INT8 = 311.9 → 1203.5 ms on NX (×3.86), 98.5 → 459.1 ms on AGX (×4.66). INT4 (BitsAndBytes) cuts LM VRAM ~47% but raises time-per-output-token by ~56% for Qwen3-VL (111.1 → 173.1 ms on NX); an AWQ W4A16 check kept TPOT near baseline, so the penalty is attributed to the BitsAndBytes execution path. — [arXiv 2607.08029 HTML](https://arxiv.org/html/2607.08029)

**FlashDrive (arXiv 2608.12932; 13 Aug 2026; Li, Liang, Zhang, Chen, Liang, Liu)**
- [P] Driving VLA (Alpamayo 1.5-10B), not manipulation. RTX PRO 6000: 716.9 → 151.4 ms (4.7×); stages before → after: encode 87.0 → 12.0, prefill 165.3 → 47.2, decode 271.7 → 45.3, action (flow matching) 192.9 → 46.9 ms. Jetson Thor single trajectory 3770.3 → 943.6 ms (4.0×). — [arXiv 2608.12932 HTML](https://arxiv.org/html/2608.12932)
- [P] CUDA Graph + kernel fusion together give 1.40× (716.9 → 513.3 ms); the paper states the pipeline launches hundreds of small kernels per forward pass so CPU dispatch overhead is significant at batch 1; prefill (one long matmul) sees no meaningful gain. Adaptive step caching: 8 flow steps, 4 middle steps reuse cached velocity, action latency 113.9 → 47.6 ms, minADE6 0.770 → 0.812 m. Closed-loop check exists (AlpaSim, 100 clips) but is not tied to device latency. — [arXiv 2608.12932 HTML](https://arxiv.org/html/2608.12932)

**NanoVLA (arXiv 2510.25122; 29 Oct 2025; Chen, Wang, Chen, Cai, Lu)**
- [P] Measures on **Jetson Orin Nano Super Developer Kit 8 GB**. Claims 52× higher FPS than OpenVLA (the OpenVLA figure is from its 4-bit Llama2 backbone because full 4-bit OpenVLA ran OOM). Versus SmolVLA: NanoVLA with 10 action-chunk steps is 17.1% slower; with 50 action-chunk steps it has 43.8% higher FPS and +3.2 points success. Only relative FPS vs SmolVLA is given in the text; software stack unspecified beyond CUDA (no TensorRT/quantization); no per-component split except that caching language features saves 62% of inference time per execution (Qwen 0.5B). — [arXiv 2510.25122 HTML](https://arxiv.org/html/2510.25122)
- [P] Long-short action chunking: train with 100 action-chunk steps, execute 10 at inference; ablation: both fixed and long-short chunking peak at 20 executed steps (90.2%), long-short stays high for 20–60 and falls to 84.0% at 100, fixed chunking drops to ~70–74% after 60. No success-vs-latency or cross-device success curve. — [arXiv 2510.25122 HTML](https://arxiv.org/html/2510.25122)

**EdgeVLA / EVLA (arXiv 2507.14049; 18 Jul 2025; Budzianowski et al., K-Scale)**
- [P] Qwen2-0.5B + SigLIP + DINOv2 (~1B), non-autoregressive end-effector prediction. All timing on an **A100-40GB** (OpenVLA 20 ms vs EVLA 5 ms; 16 GB vs 4 GB); **no Jetson or CPU measurement** (Jetson Nano only as motivation); no task success reported (training loss/token accuracy only). Speedup claims are internally inconsistent (7× abstract, 6× in Sec. III-B, ≈4× in Table I). — [arXiv 2507.14049 HTML](https://arxiv.org/html/2507.14049v1)

**SmolVLA paper (arXiv 2506.01844; June 2025) and LeRobot docs**
- [P] The paper reports **no inference latency (ms) or measured Hz and no Jetson result**; hardware is described only as "consumer-grade GPUs or even CPUs". Inference uses a fixed 10 flow-matching steps with **no step-count ablation**; images resized to 512×512, 64 visual tokens per frame via pixel shuffle, no tiling, **no resolution/token ablation**. — [arXiv 2506.01844 HTML](https://arxiv.org/html/2506.01844)
- [P] Chunk-size ablation (LIBERO avg): n=1 50.0; n=10 84.0; n=30 78.5; n=50 80.3; n=100 74.5. Actions executed before re-observing (at n=50): 1 → 80.3; 10 → 82.8; 30 → 70.8; 50 → 51.8. Layer skipping: N=8 75.0, N=16 78.5, N=24 79.5, N=32 80.3. Expert width ×{1.0, 0.75, 0.5, 0.25}: 82.3 / 77.5 / 80.3 / 73.8. — [arXiv 2506.01844 HTML](https://arxiv.org/html/2506.01844)
- [P] Async inference: client requests a new chunk when queue fill |A_t|/n < g; analytical no-idle condition **g ≥ (E[ℓ_S]/Δt)/n**; real-world sync vs async success 78.3% vs 73.3% average, with ~30% faster completion (13.75 s → 9.70 s) and 19 vs 9 cubes in fixed time. — [arXiv 2506.01844 HTML](https://arxiv.org/html/2506.01844)
- [P] LeRobot async docs: `actions_per_chunk` (default 50, "typical values 10–50") and `chunk_size_threshold` (default 0.7 in the table; "values around 0.5–0.6 work well") are "key parameters to tune for your setup"; "the combination of policy and device ... directly impacts the average inference latency"; "reduce your fps if you consistently run out of actions in queue"; SmolVLA needs ~2 GB vs ~14 GB for π0. Tuning is by watching the queue-size plot, not by task success. — [LeRobot async docs](https://huggingface.co/docs/lerobot/main/en/async)

Says task success is "on par with the PyTorch baseline" without publishing success numbers. — [Jetson AI Lab tutorial](https://www.jetson-ai-lab.com/tutorials/groot_n17_on_thor/)

### Inferences
- The three public SmolVLA-on-Orin-Nano latency points are mutually consistent once the stack is accounted for: ~460 ms (vla.cpp defaults, vision ~300 ms), ~287 ms (vla.cpp fastest flags, vision ~173 ms), ~190 ms (TensorRT FP16, vision ~91 ms, 10 denoise steps ~59 ms). In all three, on the Nano at 2×512 px the **vision encoder is the largest single stage**, whereas on AGX Thor under PyTorch eager the **action expert is ~77% of the call** (146.6 of 187 ms). "Where the time goes" for SmolVLA is therefore device- and stack-dependent — a point no single paper states across both device classes.
- The repo's own README numbers (vision ≈260 ms, decode step 85 → 43 ms on Orin Nano 8GB) are in the same range as the public vla.cpp Orin Nano vision figure (298.6 ms), so the vision-dominance observation on the Nano cannot be claimed as new.
- VLA-HWBench's "about a third of GR00T CPU preprocessing is spent waking 14 PyTorch worker threads" and "host CPU 5× faster on AMD" show that the weak-Arm-CPU side of the pipeline is already a recognized bottleneck on Jetson.

### Gaps
- No SmolVLA measurement on **Jetson Orin NX** was found in any source (queries: "SmolVLA Jetson Orin Nano inference latency ms action expert torch.compile TensorRT"; "lerobot SmolVLA Jetson Orin Nano inference slow async action queue empty github issue fps").
- No source gives a full vision / prefix / per-denoise-step split for SmolVLA on Orin Nano under **PyTorch eager vs torch.compile**; the public Nano numbers are from vla.cpp and TensorRT only.
- The full text of the NeurIPS-2026 workshop paper (OpenReview) could not be read (browser verification wall); it is not confirmed in the abstract that the "450M flow-matching VLA" is SmolVLA, nor which software stack was used, nor how "staleness admissibility" is defined.
- VLA-HWBench does not state the default SmolVLA step count in the fetched text (146.6 ms ≈ 10 × 14.5 ms suggests 10).

## 2. Is it documented that small action experts are bound by per-operation dispatch / CUDA kernel-launch overhead under PyTorch eager on weak CPUs? What speedups do compilation, CUDA graphs, TensorRT or C++ runtimes give for the action expert and the vision encoder separately?

### Takeaway
The mechanism (kernel execution shorter than CPU launch latency for the denoising step; hundreds to thousands of small kernels per call; CUDA-graph capture as the fix) is documented in 2026 for π0-class and driving VLAs on desktop GPUs and Thor, and measured indirectly for SmolVLA on Thor (per-step 14.5 → 2.4–2.7 ms with torch.compile). What is not documented is the specific scaling claim — that on an Orin-Nano-class CPU the SmolVLA expert's eager latency scales with layer count × steps but not with width, token count or batch.

### Cited Findings
- [P] Wall-OSS-0.5 technical report (arXiv 2605.30877; May 2026; RTX 5090 only): states "The denoising step is a memory-bound workload" and "GPU kernel execution time is shorter than the CPU launch latency, making CPU dispatch the bottleneck"; fix = capture the entire denoising step as a single CUDA Graph plus fused custom kernels (RoPE, RMSNorm, elementwise ops; 2–10× on those operators); overall ~4× over PyTorch eager; ~21 Hz at 224×224 and ~15 Hz at 448×448 with T=10. No profiling numbers shown; no edge device. — [arXiv 2605.30877 HTML](https://arxiv.org/html/2605.30877)
- [P] FlashDrive (arXiv 2608.12932): the pipeline launches hundreds of small kernels per forward pass, so CPU dispatch overhead is significant at single-batch arithmetic intensities; CUDA Graph + kernel fusion = 1.40× end-to-end, helping encode, decode and action stages most and prefill not at all. — [arXiv 2608.12932 HTML](https://arxiv.org/html/2608.12932)
- [P] VLA-HWBench (arXiv 2610.34717): on Thor, the π0.5 compile option captured the whole call in one CUDA graph and cut kernel launches from ~13k to 15 (405 → 157 ms); SmolVLA per-denoise-step cost 14.5 ms eager → 2.7 ms (reduce-overhead) / 2.4 ms (max-autotune), i.e. ~5–6× on the expert loop, giving 191 → 66.4 ms end-to-end. On the AMD APU the same compile gave only 8.6 → 5.9 ms per step. The paper explicitly does **not** claim that dispatch/launch overhead bounds small models and does not interpret the SmolVLA intercepts. — [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2)
- [P] VLA-HWBench conclusion on what bounds what after optimization: memory bandwidth limits only the few-token denoising-type stages; software overhead limits the other stages; GR00T N1.7 CPU preprocessing reaches 39% of the fastest call and is partly thread-wake overhead on the Arm host. — [arXiv 2610.34717 abs](https://arxiv.org/abs/2610.34717)
- [P] vla.cpp (arXiv 2606.08094): SmolVLA on RTX 3090: eager 174.1 ms → torch.compile 65.9 ms → vla.cpp 55.8 ms; RTX 5070: eager 175.99 ms → graph-captured PyTorch 76.26 ms → vla.cpp 74.11 ms. So ≈2.3–2.6× of SmolVLA's eager latency on desktop GPUs is removable by graph capture alone; the C++ runtime adds only ~1.03–1.18× on top. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] GR00T N1.7 on Thor (NVIDIA tutorial), action head only (4 steps): eager 68.2 ms → torch.compile 46.8 ms (1.46×) → TensorRT bf16 45.0 ms → TRT + FP8 21.1 ms → TRT + NVFP4 17.2 ms; backbone (vision + LLM): eager 47.7 → torch.compile 48.6 (no gain) → TRT bf16 27.0 → FP8 14.1 → NVFP4 13.6 ms. The action head is captured as a CUDA graph; cross-attention K/V are computed once and reused across denoise steps. — [Jetson AI Lab tutorial](https://www.jetson-ai-lab.com/tutorials/groot_n17_on_thor/)
- [P] EagleVLA (arXiv 2607.12659), π0.5 on Orin-50W: action expert 536.8 ms (naive PyTorch) → 143.9 ms (CUDA-graph reuse) → 67.6 ms (GPU-resident buffers + flow-matching unroll, which removes repeated graph invocations across denoise steps); ViT 152.3 → 71.9 → 66.6 ms; LLM 631.0 → 196.9 → 137.0 ms. Python/CPU dispatch and kernel-launch overhead are not separately quantified. — [arXiv 2607.12659 HTML](https://arxiv.org/html/2607.12659)
- [P] VLASH (arXiv 2512.01031) measures its latencies "with CUDA Graphs, kernel fusion, and torch.compile" (π0.5: 23.2 ms H100, 29.4 ms RTX 5090, 32.3 ms RTX 4090), i.e. launch-overhead removal is already standard practice in the async-VLA line. — [arXiv 2512.01031 HTML](https://arxiv.org/html/2512.01031v2)
- [P] Roofline-style studies describe the action expert as memory-bound, not launch-bound: VLA-Perf (54 FLOPs/byte; explicitly does not model kernel-launch latency) and XPUs (64.5 FLOPs/byte; 20–40% SM utilization during the expert). — [arXiv 2602.18397 HTML](https://arxiv.org/html/2602.18397); [arXiv 2604.24447 HTML](https://arxiv.org/html/2604.24447)
- [P] NeurIPS-2026 workshop abstract (450M VLA, T4 + AGX Orin): the action expert is 67% of the single-stream budget "and it batches well, while pre-fill barely does". — [NeurIPS 2026 poster 170035](https://neurips.cc/virtual/2026/170035)
- [P] Vision-encoder-specific results: TensorRT FP16 SmolVLA vision encoder 91.2 ms on Orin Nano vs 298.6 ms (vla.cpp default) / 173.1 ms (vla.cpp flash-attn) on the same class of device; RhinoVLA parallel 3-view encoding 34.52 → 24.31 ms on R1; SigLIP INT8 via BitsAndBytes is 2.4–4.7× *slower* than FP16 on Orin NX/AGX. — [HF model card](https://huggingface.co/eetmie/smolvla-base-onnx); [vla.cpp Orin Nano report](https://raw.githubusercontent.com/VinRobotics/vla.cpp/main/docs/benchmark/jetson-orin-nano.md); [arXiv 2606.07383 HTML](https://arxiv.org/html/2606.07383v4); [arXiv 2607.08029 HTML](https://arxiv.org/html/2607.08029)
- [S] General (non-VLA) evidence from search snippets only: a PyTorch dev-discuss post measuring ~4.5 µs fixed cost for a trivial eager call and calling small models "overhead-bound"; a 2026 preprint (HF papers 2605.30571) reporting that CUDA Graphs help most on fast GPUs with small decode shapes and that the gain mostly disappears on slower, bandwidth-bound GPUs (H100 vs L4); an NVIDIA forum thread titled "Very long kernel launch overhead on Jetson Orin NX". None of these is VLA-specific and none was opened in full. — [PyTorch dev-discuss](https://dev-discuss.pytorch.org/t/micro-optimizations-for-the-most-micro-of-benchmarks/1836.md); [HF papers 2605.30571](https://huggingface.co/papers/2605.30571.md); [NVIDIA forum](https://forums.developer.nvidia.com/t/very-long-kernel-launch-overhead-on-jetson-orin-nx/307370)

### Inferences
- The SmolVLA numbers in VLA-HWBench imply that ~80% of the eager per-step time on Thor is software overhead (14.5 → 2.4–2.7 ms per step for a ~100M expert), and "batches well" in the NeurIPS workshop abstract is what one expects from an overhead-bound stage. Together these make the dispatch-bound explanation for small experts strongly implied by published data, but the explicit statement and the width/token/batch-invariance test on an Orin Nano are not published. A small, controlled scaling experiment (vary width, suffix tokens, batch, layers, steps; eager vs CUDA-graph) on Orin Nano would be a documented-mechanism-new-evidence contribution, not a new mechanism.
- Two explanations coexist in the literature for the same stage: "memory-bound" (roofline papers, π0-size experts) and "launch/dispatch-bound" (Wall-OSS, FlashDrive, VLA-HWBench compile results). VLA-HWBench reconciles them for large models (bandwidth binds after software overhead is removed). For a 100M expert on a 6-core A78AE host, which regime holds after compilation is not reported anywhere found.
- The one generic snippet claiming CUDA-graph gains vanish on slow bandwidth-bound GPUs cuts against assuming large graph-capture gains on Orin Nano; the Thor result (5–6× per step) and the AMD result (1.5× per step) show the gain is platform-dependent. This needs measurement rather than citation.

### Gaps
- No paper found states or tests "latency scales with layer count and denoise steps but not with width, token count or batch" for a small action expert on a Jetson-class CPU (queries: "PyTorch eager small transformer Jetson Orin Nano CPU overhead kernel launch per-op dispatch latency independent of batch size action expert flow matching"; plus the per-paper reads above).
- No torch.compile / CUDA-graph number for SmolVLA on Orin Nano or Orin NX was found; torch.compile results exist only for Thor, the AMD APU and desktop GPUs.
- Separate action-expert vs vision-encoder speedups for SmolVLA under TensorRT on the Nano exist only in an undated community model card with synthetic inputs and no eager baseline.

## 3. Has any paper connected measured device latency to closed-loop task success, or shown that the success-optimal steps / resolution / chunk length / replan interval depends on the device? Any latency-aware, deadline-aware, anytime or Pareto analysis in closed loop?

### Takeaway
Pieces exist — success vs execution horizon on an Orin Nano (vla.cpp), a steps × execution-horizon factorial with measured latency (NeurIPS-2026 workshop), device-dependent minimum execution horizon and device-dependent real-robot scores (FASTER), success vs injected delay (RTC, VLASH, EagleVLA), and success with latency charged in simulated time (DASH) — but no paper found selects steps, resolution, replan interval and chunk length jointly per device to maximize closed-loop success, and none shows that the success-optimal setting moves with the device's measured latency.

### Cited Findings
- [P] OpenVLA (arXiv 2406.09246; 2024) is the earliest clear instance of "device speed changes closed-loop success": bfloat16 71.3 ± 4.8%, int8 58.1 ± 5.1%, int4 71.9 ± 4.7% on 8 BridgeData tasks; int8 ran at only 1.2 Hz on an A5000 (int4 at 3 Hz) and the authors "attribute the performance loss to low inference speed", since offline token accuracy was comparable. It is the authors' interpretation, not a controlled latency sweep. — [arXiv 2406.09246 HTML](https://arxiv.org/html/2406.09246)
- [P] vla.cpp (arXiv 2606.08094): SmolVLA on Orin Nano, success vs execution horizon S (82/86/94/88/98/80/38% for S = 1/2/4/8/16/32/50); GR00T N1.7 success vs flow steps T on RTX 3060 (flat, 95–99%); injected delay 0–2000 ms on ALOHA (9–10/10); UR10e + SmolVLA across four backends with 33× latency spread (success 12–15/20, blocked time 8% → 73%). The paper explicitly does not test whether the best execution horizon depends on latency or device. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] "Same Scene, Different Answer: Variance and Rollout Budgets for Flow-Policy Evaluation" (Gunukula; NeurIPS 2026 workshop poster): a powered **4 × 3 factorial of denoising steps × execution horizon** on released π0.5 / π0 checkpoints on LIBERO; on π0.5 "a single Euler step at horizon 10 is statistically indistinguishable from the 10-step default" at **2.7× lower measured latency**, so the shipped default is dominated; π0 does not tolerate the same step reduction; the cut costs 4.7 points under camera-viewpoint shift; replanning every step costs 9–41 points under perturbation. Hardware and latency protocol are not stated on the page; no device dimension. Also: re-running the 500-episode LIBERO protocol with only the flow-sampling seed changed gives a 2.2-point spread. — [NeurIPS 2026 poster 178329](https://neurips.cc/virtual/2026/178329)
- [P] FASTER (arXiv 2603.19199; v3 16 May 2026): reaction-time model Δt_react ~ U(Δt_infer, Δt_infer + Δt_exec) for async (mean Δt_infer + 0.5·Δt_exec), and a **device-dependent minimum execution horizon s_min = ⌈Δt_infer/Δt_ctrl⌉**: π0.5 async at 30 Hz has TTFA 80.0 ms and s_min = 3 on RTX 4090 but 303.3 ms and s_min = 10 on RTX 4060 (X-VLA: 113.7 ms / 4 vs 399.5 ms / 12). Real-robot table tennis mean score, RTX 4090 vs RTX 4060: sync 0.000 / 0.000; naive async 0.200 / 0.200; training-time RTC 0.533 / 0.300; FASTER 0.800 / 0.467. The d and s used per GPU are tabulated but there is no sweep of N or s against success, and the limitations note the method trades responsiveness for accuracy. — [arXiv 2603.19199 HTML](https://arxiv.org/html/2603.19199v3)
- [S] FASTER also states that simulation benchmarks "are not directly affected by inference latency", i.e. LIBERO/CALVIN numbers do not charge wall-clock time. — [FASTER PDF via search snippet](https://arxiv.org/pdf/2603.19199)
- [P] EagleVLA / Jetson-PI (arXiv 2607.12659): on-device measured latency is converted to a delay Δ in action steps, executed actions per chunk L = H − Δ (H = 20). LIBERO π0.5 success averaged over Δ = 1–9 (Spatial/Object/Goal/10): sync 97.3/99.6/96.7/93.5; VLASH 74.4/86.1/84.2/81.3; RTC 92.6/96.6/94.1/86.4; ours + scheduling 97.4/98.6/96.8/92.5. At Δ = 9 VLASH falls to 30.1 on Spatial. Real robot (XR-1 on Orin, 10 trials): picking 10/10 (RTX 4090) vs 6/10 (naive async on Orin) vs 10/10 (EagleVLA); folding 7/10 vs 0/10 vs 8/10. Fixed 10 denoise steps and 224×224; **no sweep of steps, resolution, replan interval or chunk length, and no study of device-dependent optima**. — [arXiv 2607.12659 HTML](https://arxiv.org/html/2607.12659)
- [P] DASH (arXiv 2611.11854; 12 Nov 2026; XPENG Robotics): simulation with **latency charged in simulated time** (RoboTwin, 50 tasks); sync success 64.5 / 66.4 / 63.6 / 62.7% for 0.8B / 2B / 4B / 8B backbones (sync latency 103 / 132 / 183 / 243 ms on RTX 4090), i.e. success stops improving as the backbone slows; decoupled async + desynchronized training reaches 65.5 / 69.1 / 69.5 / 65.9%. Only RTX 4090 latency; 4 flow steps fixed; no injected-latency sweep and no per-device setting choice. — [arXiv 2611.11854 HTML](https://arxiv.org/html/2611.11854)
- [P] "What Makes a VLA Reactive? A Study of Execution Strategies for Dynamic Manipulation" (arXiv 2611.15491; 11 Nov 2026; CoRL 2026 workshop paper): π0.5 on two dynamic sim benchmarks and three real tasks; best prediction horizon ≈ 1 s of motion (H = 25 on DOM, 30 on DOMINO); best execution horizon depends on the checkpoint (1k-step checkpoint peaks at s = 5, 5k-step at s = 15); short horizons help more under async; "Lower latency alone did not help" (RTC matches FASTER despite higher latency). **Latency was not injected or varied as a controlled variable; hardware (A100 / RTX 5090) differs between tasks; denoise steps and resolution not varied.** — [arXiv 2611.15491 abs](https://arxiv.org/abs/2611.15491); [arXiv 2611.15491 HTML](https://arxiv.org/html/2611.15491)
- [P] "Toward Real-Time VLAs: Stage-Aware Two-Step Flow Denoising and System-Level Evaluation" (arXiv 2609.39822; v2 3 Oct 2026): per-layer latency accounting on a real bimanual robot (camera readout 32.8 ms, proprio 26.4 ms, command-to-motion 15.3 ms, π0.5 10-NFE 61.6 ms on RTX 4090 D). Inference rate, publication rate and NFE were chosen per method "from preliminary experiments on this platform"; 2-NFE cuts model time 61.6 → 22.0 ms but success drops (Legato 5 NFE 29/30 → Legato + 2 NFE 26/30); higher replanning rate alone did not win. Single device; no transfer rule. — [arXiv 2609.39822 HTML](https://arxiv.org/html/2609.39822v2)
- [P] XPUs (arXiv 2604.24447): success vs number of stale denoise steps on a real arm (92/86% → 50/42% at 7 stale steps) — a freshness-vs-compute trade measured in closed loop, with speedup that varies by device (1.32× on 4090, 1.14× on AGX Orin, ~1.0× on NPUs), but the stale-step count is fixed offline and not chosen per device. — [arXiv 2604.24447 HTML](https://arxiv.org/html/2604.24447)
- [P] RTC (arXiv 2506.07339): real-world π0.5 with injected +100 / +200 ms delay (d ≈ 11 / 16 steps at 50 Hz): RTC throughput unchanged, synchronous inference degrades roughly linearly, temporal ensembling triggers protective stops. — [arXiv 2506.07339 HTML](https://arxiv.org/html/2506.07339v2)
- [P] VLASH (arXiv 2512.01031): Kinetix success at delay 4 steps 81.7% (VLASH) vs 51.2% (naive async); LIBERO success vs delay 0–3 for π0.5 and SmolVLA (SmolVLA sync 79.0; VLASH 77.1 / 78.1 / 79.1 at delay 1 / 2 / 3); max reaction latency D + 2L (sync) vs 2L (async); "the smallest offset δ greater than the measured latency Δ is selected" at deployment. No rule linking execution horizon to delay; three desktop/server GPUs only. — [arXiv 2512.01031 HTML](https://arxiv.org/html/2512.01031v2)
- [P] Chef Robotics blog (7 May 2026), "Latency-Aware VLAs with System Identification": "latency-aware" means shifting the training target by the measured composite delay (inference ~55 ms / 71 ms for 3 / 4 cameras at 10 steps on RTX 5090, leader–follower lag ~67 ms, camera jitter 5–30 ms; ≈3 ± 2 steps at 30 Hz). Reports smoothness only (−64.9% velocity discontinuity), no task success; steps and chunk length are fixed. — [Chef Robotics blog](https://www.chefrobotics.ai/post/latency-aware-vision-language-action-models-vlas-with-system-identification-for-real-time-robot-control)
- [P] Profiling papers that stop at latency: VLA-HWBench ("few action-generation iterations" is a latency recommendation, no success), VLA-Perf (success out of scope; staleness effect left to future work), 2603.02271, LiteVLA-Edge, EdgeVLA, the TensorRT model card. — [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2); [arXiv 2602.18397 HTML](https://arxiv.org/html/2602.18397)
- [S] A CMU MSR thesis (July 2026, "Beyond Vision-Language-Action Models: Adapting, Steering, and Accelerating") is described in a search snippet as proposing a latency-adaptive schedule that lets a single model handle varying inference latency and emit actions in one denoising step. The PDF exceeded the fetch size limit and could not be read. — [CMU RI thesis PDF](https://publications.ri.cmu.edu/storage/publications/2026/07/MSR_Thesis_sungjae_final_20260722153323.pdf)
- [P] GeoAAC (arXiv 2609.20776; 17 Sep 2026): training-free adaptive execution horizon chosen from the geometry of the denoising trajectory (e.g., RoboCasa365 75.1% vs 66.4% best fixed horizon; real-world 74.4% vs 53.3% for fixed-50) — adaptive replan interval, but driven by prediction reliability, with no latency or hardware in the loop. — [alphaXiv 2609.20776](https://www.alphaxiv.org/abs/2609.20776.md)

### Inferences
- LIBERO-style success sweeps (vla.cpp Fig. 5, the NeurIPS factorial, VLASH/EagleVLA with delay "in steps") do not measure the freshness effect of a slow device, because the simulator does not advance during inference unless delay is injected. The vla.cpp Orin Nano result therefore shows the open-loop-commitment effect of S, not the candidate's "slower setting acts on older observations" effect. Only real-robot studies (FASTER 4090 vs 4060; EagleVLA Orin vs 4090; vla.cpp UR10e backends), DASH's time-charged simulator and injected-delay studies capture it.
- The closest thing to a per-device configuration rule in print is a feasibility bound, not an optimum: s_min = ⌈Δt_infer/Δt_ctrl⌉ (FASTER), d ≤ s ≤ H − d (RTC), g ≥ (E[ℓ]/Δt)/n (SmolVLA), L = H − Δ (EagleVLA). None of these picks steps or resolution, and none optimizes success.
- The evidence that fewer flow steps often cost nothing in success (vla.cpp T sweep; π0.5 one-step result) plus evidence that latency hurts on dynamic tasks (FASTER, VLASH, OpenVLA int8) already implies the candidate's qualitative claim. The novel part would be the quantitative, device-indexed optimum and the inclusion of resolution.
- Statistical power is a known trap: a 2.2-point seed spread at 500 episodes (NeurIPS workshop) and 10–50 episode cells in vla.cpp mean a per-device optimum needs large rollout budgets or paired designs to be credible.

### Gaps
- No paper found that (a) measures a device's latency for each (steps, resolution, chunk, replan) setting, (b) charges that latency in closed loop, and (c) reports that the argmax-success setting differs between devices. Queries tried: "latency-aware VLA inference configuration denoising steps closed-loop success edge device Jetson"; "\"deadline-aware\" OR \"latency-aware\" OR \"anytime\" vision-language-action adaptive denoising steps control frequency task success hardware-dependent"; "VLA inference latency injected delay closed-loop success optimal execution horizon depends on latency freshness staleness trade-off flow steps"; "VLA benchmark simulation time advances during inference latency charged real-time evaluation success vs inference speed hardware Pareto denoising steps resolution".
- No "deadline-aware" or "anytime" VLA inference paper with closed-loop evaluation across devices was found; FASTER's early stopping and the unread CMU thesis are the nearest.
- The factorial paper's hardware, exact levels and equivalence test are not on the poster page; OpenReview was not readable.

## 4. Effect of the number of flow/diffusion steps on closed-loop success (π0, SmolVLA, GR00T), and of execution horizon / replan interval / chunk length; results where a chunk shorter than the inference delay breaks an async pipeline

### Takeaway
Published sweeps mostly show success is flat in the number of flow steps for GR00T N1.7 and π0.5 (down to one step) while π0 is less tolerant and a 2-step variant cost ~10 points on a real folding task; SmolVLA has no published step-count-vs-success ablation. Execution horizon has a clear interior optimum (SmolVLA: ~10 of 50 in its paper, 16 of 50 on Orin Nano in vla.cpp), and the feasibility condition tying chunk length to inference delay is stated in several papers (d ≤ s ≤ H − d; g ≥ (E[ℓ]/Δt)/n) with collapse of naive async at large delay shown empirically.

### Cited Findings
**Number of flow/denoising steps**
- [P] GR00T N1.7 (vla.cpp, RTX 3060, LIBERO, 100 episodes): T = 1/2/4/8/16 → 99/95/98/98/95% (runtime), 96/98/94/95/97% (PyTorch); latency 13.9 + 5.8·T ms for backbone + head. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] π0.5 vs π0 (NeurIPS 2026 workshop factorial): π0.5 with one Euler step at horizon 10 is statistically indistinguishable from the 10-step default at 2.7× lower latency; π0 does not tolerate the reduction; −4.7 points under camera-viewpoint shift. — [NeurIPS 2026 poster 178329](https://neurips.cc/virtual/2026/178329)
- [P] π0.5 real robot (arXiv 2609.39822): two-stage 2-NFE vs 5 NFE with the same execution method: 26/30 vs 29/30 on T-shirt folding; model time 61.6 ms (10 NFE) → 22.0 ms (2 NFE); the authors note fewer NFE does not reduce time proportionally. — [arXiv 2609.39822 HTML](https://arxiv.org/html/2609.39822v2)
- [P] SmolVLA: fixed 10 steps, no ablation in the paper; the only step-related SmolVLA data found are latency fits (14.5 ms/step eager on Thor) and a vla.cpp solver diagnostic where the max action difference between runtimes grew from 0.26 at one Euler step to 1.05 at eight. — [arXiv 2506.01844 HTML](https://arxiv.org/html/2506.01844); [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2); [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] Defaults in use: π0/π0.5 10 steps (RTC real-world runs use 5), GR00T N1.x 4 steps, DASH head 4 steps, Diffusion Policy 100 steps (which makes the "smaller" model slower: 378 ms on RTX 4090). — [arXiv 2506.07339 HTML](https://arxiv.org/html/2506.07339v2); [Jetson AI Lab tutorial](https://www.jetson-ai-lab.com/tutorials/groot_n17_on_thor/); [arXiv 2611.11854 HTML](https://arxiv.org/html/2611.11854); [arXiv 2604.24447 HTML](https://arxiv.org/html/2604.24447)
- [P] Latency side: steps scale action-expert latency linearly (VLA-Perf: 10 → 50 steps = 5× action, 2.15× end-to-end); FlashDrive reuses cached velocity for 4 of 8 steps (minADE6 +0.04 m); XPUs DP-Cache S=4 keeps π0 LIBERO 62.6 → 62.0 at 1.29×, π0.5 real robot 76% → 70%. — [arXiv 2602.18397 HTML](https://arxiv.org/html/2602.18397); [arXiv 2608.12932 HTML](https://arxiv.org/html/2608.12932); [arXiv 2604.24447 HTML](https://arxiv.org/html/2604.24447)
- [S] Unverified secondary items: a blog review of a one-step flow-matching paper reporting 95.6% on LIBERO-Long at one step with a biased (α = 4) schedule vs 70.2% for uniform, with the α = 4 model dropping to 63.4% at ten steps; FM-Steer (CVPR 2026) ablation 98.6 vs 95.9 without cascaded denoising. — [blog review](https://mcobzarenco-fontaine-blog.static.hf.space/papers/one-step-menu.html); [FM-Steer notes](https://en.papernotes.org/CVPR2026/robotics/fm-steer_enhance_generalist_policies_with_value-guided_cascaded_denoising/)

**Execution horizon / replan interval / chunk length**
- [P] SmolVLA paper: executed actions before re-observing at n = 50: 1 → 80.3, 10 → 82.8, 30 → 70.8, 50 → 51.8; chunk size n: 1 → 50.0, 10 → 84.0, 30 → 78.5, 50 → 80.3, 100 → 74.5. — [arXiv 2506.01844 HTML](https://arxiv.org/html/2506.01844)
- [P] vla.cpp, SmolVLA on Orin Nano (H = 50): best S = 16 (98%), S = 1 only 82%, S = 50 38% (attributed to never re-observing within the chunk). — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] NanoVLA: peak at 20 executed steps (90.2%); long-short chunking degrades more gracefully than fixed chunking beyond 60. — [arXiv 2510.25122 HTML](https://arxiv.org/html/2510.25122)
- [P] π0.5 on dynamic tasks (arXiv 2611.15491): best prediction horizon ≈ 1 s; best execution horizon is checkpoint-dependent (s = 5 vs s = 15); on a conveyor at s = 10, sync reaches 20% and async methods 60–75%; changing execution horizon gave as much gain as policy adaptation on the conveyor task. — [arXiv 2611.15491 HTML](https://arxiv.org/html/2611.15491)
- [P] RTC: long execution horizon reduces responsiveness, short one increases mode-jumping; only RTC and BID improve consistently as execution horizon decreases (Kinetix, d = 1). — [arXiv 2506.07339 HTML](https://arxiv.org/html/2506.07339v2)
- [P] NeurIPS factorial: replanning every step costs 9–41 points under perturbation (π0.5 / π0, LIBERO). — [NeurIPS 2026 poster 178329](https://neurips.cc/virtual/2026/178329)
- [P] GeoAAC: adaptive horizon beats the best fixed horizon (GR00T N1.5 LIBERO 95.5 vs 94.7 at h = 8; π0.5 98.0 vs 97.1 at h = 5). — [alphaXiv 2609.20776](https://www.alphaxiv.org/abs/2609.20776.md)

**Chunk shorter than (or comparable to) the inference delay**
- [P] RTC: inference delay d = ⌊δ/Δt⌋; real-time constraint d ≤ s ≤ H − d ("So long as d ≤ H − s, then this strategy will satisfy the real-time constraint"); with H = 8 the maximum supported delay is 4 steps; otherwise an action is not guaranteed to be ready when needed. — [arXiv 2506.07339 HTML](https://arxiv.org/html/2506.07339v2)
- [S] A2C2, "Leave No Observation Behind" (arXiv 2509.23224): if the execution horizon is shorter than the delay the robot has no action to run during inference and must wait; the horizon must not exceed H − d (d ≤ e ≤ H − d). Search-snippet level only. — [arXiv 2509.23224 HTML](https://arxiv.org/html/2509.23224v1)
- [P] SmolVLA: no-idle condition g ≥ (E[ℓ_S]/Δt)/n; at g = 0 the robot is "incapable of acting" for the round trip. — [arXiv 2506.01844 HTML](https://arxiv.org/html/2506.01844)
- [P] LeRobot docs: if server and client run at different speeds "the client might end up with an empty queue ... reduce your fps if you consistently run out of actions in queue"; larger `actions_per_chunk` reduces the chance of running out of actions but may be less precise. — [LeRobot async docs](https://huggingface.co/docs/lerobot/main/en/async)
- [P] HF × NXP blog: "end-to-end inference latency must remain shorter than the action execution duration" ("inference time < execution time"); example uses 100 actions per chunk at 60 FPS with threshold 0.2. — [HF/NXP blog](https://huggingface.co/blog/nxp/bringing-robotics-ai-to-embedded-platforms)
- [P] FASTER: s_min = ⌈Δt_infer/Δt_ctrl⌉ (10–12 steps on an RTX 4060 at 30 Hz). — [arXiv 2603.19199 HTML](https://arxiv.org/html/2603.19199v3)
- [P] Empirical collapse with large delay relative to the chunk: Kinetix H = 8, delay 4: naive async 51.2% vs VLASH 81.7%; EagleVLA H = 20, Δ = 9: VLASH 30.1% on LIBERO-Spatial vs 97.3% for the corrected method; RTC real-world: temporal ensembling could not run at +100 / +200 ms (protective stops). — [arXiv 2512.01031 HTML](https://arxiv.org/html/2512.01031v2); [arXiv 2607.12659 HTML](https://arxiv.org/html/2607.12659); [arXiv 2506.07339 HTML](https://arxiv.org/html/2506.07339v2)
- [P] vla.cpp README: the policy should run on a GPU host because "on a desktop CPU the action queue stalls"; UR10e runs show blocked-on-prediction time rising to 73% at 3.65 s latency. — [vla.cpp repo](https://github.com/VinRobotics/vla.cpp); [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)

### Inferences
- For a short-chunk model (the repo's FAST-DCT variant emits a chunk of 10), the published feasibility bound d ≤ H − d means that at 30 Hz the inference delay must be ≤ 5 control steps (≈167 ms) for an RTC-style async overlap, and the SmolVLA condition g ≥ (ℓ/Δt)/n cannot be met at all once ℓ/Δt > n (i.e. latency > 333 ms at 30 Hz, n = 10). Public Orin Nano SmolVLA latencies of 190–460 ms sit at or beyond that bound, so "chunk shorter than inference delay breaks the async pipeline" is a direct consequence of published constraints — it is established as a rule, though not demonstrated as an experiment on a Jetson.
- Since step count barely moves success for π0.5 / GR00T while cutting latency linearly, the freshness-vs-fidelity trade for steps may be nearly one-sided on those models (fewer steps dominate). Whether the same holds for SmolVLA (not distilled, 10-step default, π0-like sensitivity possible) is untested in the literature — that is where a trade-off, and hence a device-dependent optimum, could actually exist.

### Gaps
- No published SmolVLA closed-loop success vs number of flow steps (query: "number of flow matching denoising steps ablation success rate pi0 SmolVLA GR00T \"denoising steps\" LIBERO one-step vs 10 steps").
- No experiment found that runs an async pipeline on a Jetson with a chunk deliberately shorter than the measured delay and reports the failure mode.
- Exact Kinetix numbers for RTC vs delay/execution horizon are in figures only.

## 5. Input-resolution changes at inference time for VLAs (accuracy drop without retraining, multi-resolution training, any-resolution / elastic models applied to VLAs)

### Takeaway
Resolution is the least-studied axis: for VLAs there are train-time comparisons (OpenVLA: 224 vs 384 no success difference at 3× training cost) and latency scaling results (pre-fill ≈ 23 ms + 464 ms/megapixel for a 450M VLA; Wall-OSS 21 Hz at 224 vs 15 Hz at 448), but I found no closed-loop study of changing a VLA's input resolution at inference without retraining, and no VLA with FlexiViT/NaViT/Matryoshka-style elastic resolution or token budgets.

### Cited Findings
- [P] OpenVLA: tested 224×224 vs 384×384 and "found no performance difference in our evaluations", while the larger size takes ~3× longer to train; the authors note higher resolution helps VLM benchmarks but they "did not see this trend (yet) for VLAs". This is train-at-each-resolution, not inference-time switching. — [arXiv 2406.09246 HTML](https://arxiv.org/html/2406.09246)
- [P] SmolVLA: 512×512, 64 visual tokens per frame after pixel shuffle, global image only (no tiling); no resolution or token-count ablation. — [arXiv 2506.01844 HTML](https://arxiv.org/html/2506.01844)
- [P] NeurIPS-2026 workshop (450M VLA, T4 + AGX Orin): latency follows encoder pixel work (images × resolution), not the number of visual tokens the LM sees; pre-fill ≈ 23 ms + 464 ms/megapixel; three 256-px cameras batch better than one 512-px camera. Action-error effects of resolution are not stated in the abstract. — [NeurIPS 2026 poster 170711](https://neurips.cc/virtual/2026/170711)
- [P] Wall-OSS-0.5 (RTX 5090, three views): ~21 Hz at 224×224 vs ~15 Hz at 448×448 at T = 10; notes ViT compute grows quadratically with image tokens and a longer visual context inflates the KV cache. — [arXiv 2605.30877 HTML](https://arxiv.org/html/2605.30877)
- [P] RhinoVLA: picks a backbone with 64 merged visual tokens per image (vs 256 for PaliGemma-224) on the argument that visual/context tokens drive latency; no token-count ablation of its own; resolution stated inconsistently (224 vs 256). — [arXiv 2606.07383 HTML](https://arxiv.org/html/2606.07383v4)
- [P] Fragility signal for inference-time changes in SmolVLA's vision path: a precision change that shifted position-embedding indices dropped LIBERO-Object task-0 success to 2/10 (9/10 after matching the reference). — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] vla.cpp's Orin Nano table shows resolution/view count tracking vision time across models: SmolVLA 2 × 512 px → 298.6 ms vision; π0 2 × 224 px → 169.2 ms; GR00T N1.7 1 × 256 px → 82.3 ms; Evo-1 1 × 448 px → 523.3 ms (different encoders, so indicative only). — [vla.cpp Orin Nano report](https://raw.githubusercontent.com/VinRobotics/vla.cpp/main/docs/benchmark/jetson-orin-nano.md)
- [S] Elastic-token work exists for VLMs, not VLAs: Matryoshka Query Transformer (arXiv 2405.19315; any number of visual tokens at inference), Matryoshka Multimodal Models (ICLR 2025; nested coarse-to-fine token sets), PARCEL (arXiv 2605.30126; one model across 16–256 tokens). The search for VLA applications returned none. — [arXiv 2405.19315](https://arxiv.org/pdf/2405.19315); [M3, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/722fcbc1a6667f2075d75ea79a1b3552-Abstract-Conference.html); [arXiv 2605.30126](https://arxiv.org/html/2605.30126)
- [B] FlexiViT (arXiv 2212.08013; randomized patch size during training so one ViT runs at many sequence lengths) and NaViT (arXiv 2307.06304; native-resolution, variable-length ViT) are the standard any-resolution references; neither is a VLA result. — [arXiv 2212.08013](https://arxiv.org/abs/2212.08013); [arXiv 2307.06304](https://arxiv.org/abs/2307.06304)
- [S] The VLA efficiency literature attacks visual cost through token pruning/compression rather than resolution: VLA-Pruner (arXiv 2511.16449), Compressor-VLA (arXiv 2511.18950; −59% FLOPs, >3× fewer visual tokens on LIBERO), EfficientVLA (training-free, 0.6% success drop on SIMPLER per snippet), BLURR (arXiv 2512.11769; keeps 224×224). — [arXiv 2511.16449 HTML](https://arxiv.org/html/2511.16449v3); [arXiv 2511.18950 HTML](https://arxiv.org/html/2511.18950v1); [arXiv 2512.11769 HTML](https://arxiv.org/html/2512.11769v1)

### Inferences
- The NeurIPS workshop finding (latency follows pixels, not LM tokens) plus the Orin Nano numbers (vision is the biggest SmolVLA stage at 2 × 512 px) mean that on Nano-class devices resolution is the single largest latency lever, yet it is the one axis with no closed-loop evidence. Token pruning after the encoder, the dominant approach in the literature, does not reduce encoder pixel work.
- Because SmolVLA's connector pixel-shuffles to a fixed 64 tokens at 512 px, lowering resolution changes both the SigLIP position-embedding grid and the token count; the vla.cpp index-precision incident suggests naive inference-time resolution changes can fail sharply rather than gracefully, so multi-resolution fine-tuning is the likely requirement. This is an inference; no paper tests it.

### Gaps
- No VLA paper found that (a) changes resolution at inference without retraining and reports closed-loop success, (b) trains a VLA with multiple resolutions for run-time selection, or (c) applies FlexiViT / NaViT / Matryoshka token budgets to a robot policy. Queries: "VLA input resolution inference time robustness visual token budget elastic Matryoshka FlexiViT robot policy success drop"; "VLA lower image resolution at inference without retraining success rate drop 224 vs 448 multi-resolution training robot policy"; "Matryoshka OR elastic OR \"any-resolution\" visual tokens vision-language-action policy adjustable token budget at inference single model"; "OpenVLA 224 vs 384 resolution no performance difference; VLA image resolution ablation success rate pi0 448 FlexiViT NaViT robot".
- VLANeXt (arXiv 2602.18532) and SimVLA (NeurIPS 2026) are controlled VLA design-ablation papers that may contain resolution ablations; they surfaced in search but were not opened.

## 7. Verdict for the candidate idea, closest papers, remaining gap, and what is already established about SmolVLA-on-Jetson latency

### Takeaway
**Verdict: partially done.** Each ingredient has been published separately in 2026 — success vs execution horizon on an Orin Nano, success vs flow steps with measured latency, device-dependent minimum execution horizon, success vs delay, latency-charged simulation — but no paper found performs joint, per-device selection of (flow steps, resolution, replan interval, chunk length) to maximize closed-loop success under the device's measured latency, and none shows the success-optimal configuration shifting between devices. The resolution axis and SmolVLA-specific step sensitivity are untouched in closed loop.

### Cited Findings
**Closest papers, in order of overlap with the candidate**
1. [P] vla.cpp (arXiv 2606.08094): SmolVLA on Orin Nano with a closed-loop execution-horizon sweep (optimum S = 16 of 50), a flow-step sweep with success (GR00T, desktop), delay injection, the rate model f_exec ≈ S/(L_rt + S·Δt), and the statement that comparisons must specify both S and T. Does not vary resolution, does not charge latency in simulation, and explicitly does not test device dependence of the optimum. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
2. [P] "Same Scene, Different Answer" (NeurIPS 2026 workshop): steps × execution-horizon factorial with measured latency showing the shipped π0.5 default is dominated. No device axis, no resolution, LIBERO only. — [NeurIPS 2026 poster 178329](https://neurips.cc/virtual/2026/178329)
3. [P] FASTER (arXiv 2603.19199): explicit reaction-time model, device-dependent s_min, and real-robot scores that differ between RTX 4090 and RTX 4060. Changes the sampling schedule rather than selecting a configuration; no sweep of steps/horizon vs success per device. — [arXiv 2603.19199 HTML](https://arxiv.org/html/2603.19199v3)
4. [P] EagleVLA / Jetson-PI (arXiv 2607.12659): on-Jetson measured delay drives L = H − Δ; success vs Δ; Orin vs 4090 real-robot comparison. Steps, resolution, chunk fixed. — [arXiv 2607.12659 HTML](https://arxiv.org/html/2607.12659)
5. [P] "What Makes a VLA Reactive?" (arXiv 2611.15491; 11 Nov 2026): systematic prediction-/execution-horizon and sync/async study on dynamic tasks; finds lower latency alone does not help and the best execution horizon is checkpoint-dependent. Latency not controlled, single hardware class per task, no steps/resolution. — [arXiv 2611.15491 HTML](https://arxiv.org/html/2611.15491)
6. [P] DASH (arXiv 2611.11854; 12 Nov 2026): success with latency charged in simulated time across backbone sizes — the evaluation mechanism the candidate needs, used to justify an architecture rather than a configuration search. — [arXiv 2611.11854 HTML](https://arxiv.org/html/2611.11854)
7. [P] VLA-HWBench (arXiv 2610.34717) and VLA-Perf (arXiv 2602.18397): supply the per-device latency model (linear in steps; chunk size nearly free) but no success; VLA-Perf explicitly leaves the staleness-to-success link as future work. — [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2); [arXiv 2602.18397 HTML](https://arxiv.org/html/2602.18397)
8. [P] OpenVLA (arXiv 2406.09246): first documented case that a slower inference setting lowered real-robot success despite equal offline accuracy (int8 at 1.2 Hz: 58.1% vs 71.3–71.9%). — [arXiv 2406.09246 HTML](https://arxiv.org/html/2406.09246)
9. [P] NeurIPS-2026 workshop "Where Edge VLA Latency Actually Goes" (450M VLA on T4 / AGX Orin): resolution-latency scaling law and "staleness admissibility" for prefix caching vs quantization, in open-loop action error. — [NeurIPS 2026 poster 170035](https://neurips.cc/virtual/2026/170035)
10. [P] Feasibility rules that any per-device configurator must respect and cannot claim: d ≤ s ≤ H − d (RTC), g ≥ (E[ℓ_S]/Δt)/n (SmolVLA), s_min = ⌈Δt_infer/Δt_ctrl⌉ (FASTER), "inference time < execution time" (HF/NXP), "reduce fps if you run out of actions" (LeRobot docs). — [arXiv 2506.07339 HTML](https://arxiv.org/html/2506.07339v2); [arXiv 2506.01844 HTML](https://arxiv.org/html/2506.01844); [arXiv 2603.19199 HTML](https://arxiv.org/html/2603.19199v3); [HF/NXP blog](https://huggingface.co/blog/nxp/bringing-robotics-ai-to-embedded-platforms); [LeRobot async docs](https://huggingface.co/docs/lerobot/main/en/async)

**Already established about SmolVLA-on-Jetson latency (cannot be claimed as new)**
- [P] SmolVLA runs on a Jetson Orin Nano 8GB within ~1.7–2.5 GB: 462.8 ms per call at defaults (2 × 512 px, 10 flow steps) and 286.7 ms with fastest flags under vla.cpp; ~190 ms (5.25 Hz) under TensorRT FP16. — [vla.cpp Orin Nano report](https://raw.githubusercontent.com/VinRobotics/vla.cpp/main/docs/benchmark/jetson-orin-nano.md); [HF model card](https://huggingface.co/eetmie/smolvla-base-onnx)
- [P] On the Orin Nano the vision encoder is the largest stage (298.6 of 462.8 ms; 173.1 of 286.7 ms; 91.2 of 189.9 ms under TensorRT, where 10 denoise steps take 59.3 ms). — [vla.cpp Orin Nano report](https://raw.githubusercontent.com/VinRobotics/vla.cpp/main/docs/benchmark/jetson-orin-nano.md); [HF model card](https://huggingface.co/eetmie/smolvla-base-onnx)
- [P] SmolVLA closed-loop on the Orin Nano has been run: 176/200 on LIBERO-Object at S = 4 (141.81 ms per executed action), and success vs execution horizon peaks at S = 16 (98%) and collapses at S = 50 (38%). — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] AGX Orin: 164.3 ms per call (vla.cpp), 65.41 ms per executed action at S = 4 with 181/200. — [vla.cpp docs/benchmark](https://github.com/VinRobotics/vla.cpp/tree/main/docs/benchmark); [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] AGX Thor, PyTorch eager: 191 ms with action generation 146.6 ms (~77%), vision 20.9 ms, prefill 15.0 ms; latency is linear in flow steps (14.5 ms/step + 41 ms); torch.compile cuts the per-step cost to 2.4–2.7 ms and the call to 66–72 ms. — [arXiv 2610.34717 HTML](https://arxiv.org/html/2610.34717v2)
- [P] Graph capture alone removes most of SmolVLA's eager overhead on desktop GPUs (174–176 ms → 66–76 ms); a C++ runtime adds little beyond that. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] For a 450M flow-matching VLA on AGX Orin / T4: the action expert is 67% of the single-stream budget and batches well; pre-fill time scales with megapixels (≈23 ms + 464 ms/MP), not with LM-visible token count; vision-prefix caching costs more action error than INT8 quantization. — [NeurIPS 2026 poster 170035](https://neurips.cc/virtual/2026/170035)
- [P] The action expert is the quantization-sensitive block (keep at higher precision); vision encoder and LLM prefill tolerate quantization; SigLIP INT8 via BitsAndBytes is slower than FP16 on Orin NX/AGX. — [HF/NXP blog](https://huggingface.co/blog/nxp/bringing-robotics-ai-to-embedded-platforms); [arXiv 2607.08029 HTML](https://arxiv.org/html/2607.08029)
- [P] Small numerical changes in SmolVLA's vision position indexing can flip task success (2/10 vs 9/10), so action-agreement or cosine similarity alone is not a safe proxy for closed-loop behavior. — [arXiv 2606.08094 HTML](https://arxiv.org/html/2606.08094v2)
- [P] Execution-horizon and chunk-size sensitivity of SmolVLA (best around 10 executed actions of a 50-chunk; n = 10–50 good; n = 1 and re-observe-after-50 bad) and the async queue-threshold condition are in the original paper. — [arXiv 2506.01844 HTML](https://arxiv.org/html/2506.01844)

### Inferences
**Precise remaining gap (what would be new if done carefully)**
- A joint, device-indexed configuration study: for each device (at minimum Orin Nano 8GB plus one faster device such as AGX Orin/Thor or a desktop GPU), measure latency for every (flow steps × input resolution × executed actions per chunk × chunk length) setting, charge that latency in closed loop (real robot, or a simulator whose clock advances during inference, or injected delay equal to measured latency), and report the argmax-success setting per device. The claim to prove is that the optimum moves with the device — no paper found shows this.
- The resolution axis in closed loop: no paper found evaluates lower-resolution inference (with or without multi-resolution training) against task success, although published data show resolution is the dominant latency lever on the Nano.
- SmolVLA-specific flow-step sensitivity in closed loop: not published; existing step sweeps are for GR00T N1.7 and π0.5/π0 and disagree across models.
- A selection rule or predictor (not just a table): the literature offers feasibility bounds only; a rule that maps measured latency to a success-maximizing setting, validated on a held-out device, was not found.
- An explicit dispatch-overhead scaling test for the small action expert on an Orin-Nano-class CPU (latency vs layers/steps/width/tokens/batch, eager vs graph-captured) is unpublished, though the mechanism itself is documented for larger models and GPUs.

**Risks to the novelty claim**
- The qualitative statement ("a slower, more accurate setting acts on staler observations; evaluate in closed loop, not open loop") is already present across OpenVLA, RTC, VLASH, FASTER, DASH, VLA-Perf (as future work) and the 2611.15491 study; it should be cited, not claimed.
- On quasi-static benchmarks the trade may not appear: vla.cpp found success insensitive to 0–2000 ms injected delay on ALOHA and flat in flow steps; VLASH notes sync is a strong baseline on LIBERO. The candidate needs dynamic tasks or time-charged evaluation to show an effect at all.
- If fewer flow steps do not reduce success for the model in question (as for π0.5 and GR00T), the "fidelity" side of the trade vanishes for that axis and the result reduces to "use fewer steps", which VLA-HWBench and the NeurIPS factorial already recommend.
- The field is moving weekly: two directly relevant papers (2611.11854, 2611.15491) appeared on 11–12 Nov 2026, days before this survey date.
